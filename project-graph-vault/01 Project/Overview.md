# Overview

GemVTuber is a desktop companion that lives on the user's screen as a transparent, frameless, always-on-top Electron window hosting a VTuber avatar. Unlike face-tracked VTubing, the avatar is driven by the AI itself: microphone audio streams up to Google's Gemini Live API over a raw WebSocket, Gemini answers with its own native audio voice rather than an ASR-to-LLM-to-TTS cascade, and the same session issues function calls that set facial expressions, play motions, capture screenshots, and store memories about the user. Periodic screen captures give the model contextual awareness of what the user is doing - noticing a long gaming session, for example - while five built-in personalities (caring, playful, sarcastic, strict, chill) plus a custom prompt shape the character across sessions.

The whole product is deliberately one Electron app with no Python backend. A small main process owns the window, tray icon, config file, and screen-capture scheduling, while an esbuild browser bundle carries everything else: audio capture and playback, the Gemini WebSocket client, the PixiJS Live2D renderer, lip sync, keyframe animation, and all overlay UI. That split runs through a single contextBridge API named electronAPI, unpacked in [[Electron Main Process]]; the AI half lives in [[Gemini Live Session]], [[Tool Calling]], and [[Personality and Memory]]; the avatar half in [[Avatar Rendering]] and [[Lip Sync and Animation]]. The latency story - sub-second voice - rests on native-audio responses plus a series of deliberate optimizations documented in [[System Overview]] and [[Audio Pipeline]].

This vault exists because that pipeline spans roughly twenty source files across two processes and deserved one linked map. Audit scope covered src/main and src/renderer in full, the root configs and build scripts, the git history (55 commits, May 2026), and the repo documents; nothing was executed against the live Gemini API, and the jest suite could not be run in this workspace because jest and babel are absent from node_modules despite being declared devDependencies. Runtime behavior claims are therefore code-derived inference, marked as such where it matters; see [[Discrepancies]] for where README marketing and main-branch code currently disagree.
